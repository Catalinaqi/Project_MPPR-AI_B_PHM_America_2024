# Fase 6: Deployment

La sesta fase del ciclo CRISP-DM si occupa della **messa in produzione** del modello e della consegna degli artefatti finali.  
Nel progetto PHM North America 2024, il deployment è gestito da un runner orchestrale che esegue due tecniche sequenziali:

1. **Cascade Inference** – inferenza combinata (classificazione + regressione) su dati di test.
2. **Zip Delivery** – impacchettamento di tutti gli artefatti in un archivio ZIP.

Il runner `Phase6DeploymentRunner` carica dinamicamente modelli, calibratore e dati di test, quindi dispaccia l'esecuzione alle funzioni concrete `run_cascade_inference` e `run_zip_delivery`.

---

## 6.1 Inferenza a Cascata (Cascade Inference)

**Tecnica:** `cascade_inference`

**Obiettivo:**  
Applicare la pipeline completa di inferenza su un set di dati di test non visto:
- Il **classificatore** (LightGBM + calibrazione isotonica) calcola la probabilità di guasto.
- Il **regressore** (NGBoost) stima il margine di coppia e la sua incertezza.
- I risultati sono fusi in un unico file `parquet` con colonne di predizione, probabilità e intervallo di confidenza.

**Input atteso (da `input_source`):**
- `classification_model` – modello LightGBM serializzato (`.pkl`)
- `regression_model` – modello NGBoost serializzato (`.pkl`)
- `classification_calibrator` – calibratore isotonico (`.pkl`)
- `classification_test_data` – dataset di test per la classificazione (`.parquet`)
- `regression_test_data` – dataset di test per la regressione (`.parquet`)

**Output generato:**
- File `parquet` contenente le predizioni finali (salvato nel percorso `ctx.predictions_path`).

**Note tecniche:**  
- I modelli sono caricati all'interno della funzione `run_cascade_inference` tramite `_resolve_artifact_path`.
- Non vi è alcun ritraining o aggiornamento dei pesi; è una pura fase di **inferenza batch**.

---

## 6.2 Confezionamento degli Artefatti (Zip Delivery)

**Tecnica:** `zip_delivery`

**Obiettivo:**  
Raccogliere tutti gli artefatti rilevanti prodotti durante le fasi precedenti e impacchettarli in un unico archivio ZIP per la consegna al committente o per il versioning.

**Input atteso:**
- L'intera directory della run (`run_dir`), contenente:
  - Modelli serializzati (`.pkl`)
  - Dataset trasformati (`.parquet`)
  - Log di pipeline (`.json`)
  - Grafici e report (`.png`, `.md`)
- Il percorso di output dello ZIP è configurato nei parametri della tecnica.

**Output generato:**
- File `.zip` contenente la struttura della run (salvato in `ctx.zip_path`).

**Note tecniche:**  
- La funzione `run_zip_delivery` itera ricorsivamente sulla directory di run e comprime tutti i file.
- La struttura dello ZIP preserva la gerarchia delle fasi (phase2, phase3, phase4, phase5, phase6).

## Riepilogo Fase 6

| Sottofase | Tecnica | Input | Output |
|:---|:---|---:|---:|
| **6.1** | Cascade Inference | Modelli + test data | Predizioni (`.parquet`) |
| **6.2** | Zip Delivery | Intera run directory | Archivio ZIP |

Il runner si occupa anche di:
- Verificare l'esistenza degli artefatti prima dell'inferenza (fail fast).
- Gestire la serializzazione dei predizioni e dello ZIP tramite il context `RunContext`.
- Fornire log di tracciamento per ciascuna tecnica.

**Stato del deployment (dal certificato finale della Fase 5):**  
Il modello è stato approvato come **MVP interno** (`MVP_INTERNAL`). Il deploy su sistemi reali richiede la revisione di un ingegnere della manutenzione (`Human-in-the-Loop`) a causa dei problemi di calibrazione probabilistica (underconfidence) emersi nella Fase 5.2.
